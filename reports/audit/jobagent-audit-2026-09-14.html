The headline

JobAgent is an unusually well-engineered discovery and resume-tailoring system wearing the label of an application system. The resume tailor is genuinely excellent — provably non-fabricating, with fail-closed invariants I verified by running it. The discovery layer really does reach eleven ATS platforms. But in 54 days of real operation the pipeline has produced zero submitted applications, and the two gaps that matter most are not polish items: a fresh clone of this repository cannot run its own test suite, and the shipped example configuration will type placeholder text into real employers' work-authorization fields.

As of 2026-09-15, on branch fix/audit-2026-09-14: both of those two gaps are closed — a clean clone runs 97/97 files and 1,434 tests, and placeholder configuration now fails preflight and refuses to build a packet. The first sentence still stands: the funnel still ends at zero submissions. See the remediation log.

01

Executive assessment

What this codebase is, versus what it presents itself as

JobAgent is a 364-file, Node 22 + Python hybrid: fifteen job-source adapters, a deterministic scoring engine, a Python resume tailor driven over a stdio pipe, a Playwright form-filler, a local dashboard, and a Chromium extension. The engineering standard in the core is high and — unusually — the code comments explain why a decision was made, often citing the measurement that forced it. That is rare and valuable, and it made this audit faster.

The gap is between the system's two halves. The read half — discover, normalize, dedupe, score, tailor — is built, tested, and demonstrably running at scale. The write half — approve, fill, submit, track, learn — is built but has never completed a single cycle. Every application-side number in the database is 0 or 4.

Three structural facts shape everything below:

  • It is a single-profile system, honestly labelled as one. The README closes with "Built for a senior data engineer profile that requires visa sponsorship," and the code matches: scoring category names like azureFabricStack and biSemanticDepth are JavaScript identifiers in src/scoring/scorer.js, not config keys. A second user does not reconfigure this; they fork it.
  • The safety architecture is real but untested by use. Sponsorship-polarity guards, submit verification, write-ahead duplicate protection, human approval gates — these are genuinely well designed and I verified their logic. None of them has ever fired in anger, because nothing has ever been submitted.
  • Documentation quality outruns documentation accuracy. docs/SUPPORT_MATRIX.md is one of the better honesty documents I have read in an open-source repo, and it is stale: four shipped discovery adapters are missing from it, and one (iCIMS, 2,429 jobs found) is listed as unsupported.

P0FIXED

src/apply/screeningQA.js → src/apply/formPrefill.js:200
Problem

Coverage and quality problems

  • Half the corpus is unreadable. 53,359 of 101,857 rows have a JD under 200 characters and 51,378 are flagged summary_only. The pipeline correctly refuses to judge these, but the detail-fetch budget (maxDetailFetches: 25 for atsSearch) is far too small relative to intake.

  • The dedupe key is lossy. keyFor() is company::title only. Two genuinely different "Data Engineer" roles at the same company collapse in-batch, keeping whichever has the longer JD. Do not rebuild the adapter architecture — it is already correct. Systematic errors this design produces

  • Early saturation creates false positives. A JD mentioning Azure, Databricks and Delta Lake once each scores identically to a perfect stack match. With python + sql (12) + three Azure words (14) + a title hit (12) + Unconfirmed sponsorship (3.5 + 1) + neutral geography (3) + fresh (4), a mediocre posting clears 55 before any real fit is established.
  • Unread jobs are structurally undecidable. The pipeline comment states this precisely: with no description, the reachable maximum is ~44 against a 50 floor, so every summary-only row is a guaranteed Discard. Handling this via a needs_description bucket is the right call; leaving 5,029 of them unenriched and mislabelled is not.
  • The sponsorship prior distorts ranking. 15 of 110 points turn on a 21-name list. A Deloitte posting starts 13 points ahead of an identical posting from an unlisted employer.
  • Explanations name contributors, not reasons. buildExplanation emits "Top contributors: azureFabricStack 14/14, titleFit 12/12…". That is a score decomposition, not an answer to "why does this job match me?"
Recommended shape

Keep the deterministic core; add two stages in front and one behind it.
① Eligibility gates (hard pass/fail: work authorization, clearance, years floor, degree requirement, location legality) → ② structured requirement extraction (required vs preferred, with the LLM path already built in jdRequirements.js promoted from tailoring to scoring) → ③ the existing weighted fit with saturation raised and compensation added → ④ embedding similarity between the JD requirement set and the resume evidence map, as one additional weighted factor → ⑤ a written explanation assembled from the gates and the top three matched requirements, naming the job's words and the resume's evidence.

The core structural problem

The same facts are stated in four places that can silently disagree: the master resume ("10+ years", the Azure stack), candidate.json (technicalStack, seniority), screening_answers.json (years_experience: "10+ years"), and cover_letter.json (yearsOfExperience: "10+ years"). Nothing reconciles them. The resume is the only one of the four that is actually evidence.

Proposed Candidate Intelligence Profile

Invert the direction: parse the resume into evidence, then let the profile carry only what a resume cannot say.

  1. Evidence layer — derived, never edited. Parse the master resume into an evidence map: {skill, first_seen, last_seen, months, employers[], bullet_ids[]}. tailor.py's _resume_evidence and _audit_supported_keywords already build most of this; it just never leaves Python. Persist it as data/candidate_evidence.json, regenerated on resume change.
  2. Declared layer — facts a resume cannot carry. Contact details, work authorization, EEO answers, start date. Small, explicit, sentinel-checked.
  3. Preference layer — what you want. Unchanged from today's model, which is already good.
  4. Learned layer — what you actually do. Approvals, rejections and their reasons, per-question answers from the question queue, and outcomes per source and per employer.

Three things fall out for free. Per-skill years become answerable, which closes the P0 in §5. scoring.keywords becomes derivable rather than hand-written, which unlocks a second user. And "does this job match me" becomes a claim about evidence, not about a keyword list.

Do not change the tailor's grounding rules

The rule that resume output may only reorder and emphasize existing text, enforced by invariants that raise before save, is the single best decision in this codebase. Every fabrication risk found in this audit lives outside it — in cover letters, in screening answers, in the example config. Extend that discipline outward; do not relax it here.

Keep as-is: sponsorship polarity (a model would be less predictable on a legally sensitive field), resume rewriting (the invariants are worth more than fluency), tier thresholds, dedupe, freshness.

Architecture issues

  • Four mega-files. public/assets/js/app.js 3,938 lines · resume/tailor.py 2,262 · dashboard/server.js 1,989 · dashboard/data.js 1,862.   • Config sprawl.   • Three identity notions. job.id (source + company + title + sourceJobId), the dedupe key (company + title), and the normalized URL key. Each is defensible alone; together they mean "is this the same job?" has three answers.
  • Duplicated assets that have drifted. interview-prep/site/assets/js/ and src/dashboard/public/learn/assets/js/ are 360 KB copies of each other — and 5 of 12 files already differ. This is not a theoretical duplication cost; the two copies now serve different content.

Do not rewrite. Do not add a framework to the dashboard. Do not replace SQLite. Do not restructure the adapter registry. The module boundaries are largely right and the dependency graph is nearly acyclic — one dead module in about ninety is an excellent result. The work here is consolidation of state and configuration, not redesign.

Recommended implementation sequence

Five stages, each independently shippable
  1. Stage 1 — Stop the bleeding (~1 week)
    Every P0. Sentinel checks, the per-skill years fix, untrack the resume, make a clean clone testable, fix the sqlite import, prune .env.example, ignore PyProjects/.
    Exit criterion: a fresh clone runs green CI, and a new user cannot submit a placeholder answer.
  2. Stage 2 — Make it honest (~1 week)
    The lifecycle state machine, run-history recording, the timezone fix, the NEEDS_DESCRIPTION status, graceful PDF degradation, and a refreshed support matrix and README.
    Exit criterion: every number on the dashboard means what its label says, and every run leaves a record.
  3. Stage 3 — Close the funnel (~2 weeks)
    This is the stage that matters most. Fix screening-answer matching from the real question-queue labels, widen the ATS allowlist, build the action-queue landing, add outcome capture, and drive one application through to submitted end to end.
    Exit criterion: the funnel in this report no longer terminates at zero.
  4. Stage 4 — Make matching intelligent (~3 weeks)
    The candidate evidence layer, eligibility gates, requirement extraction promoted into scoring, declarative scoring categories, raised saturation, compensation scoring, and written explanations.
    Exit criterion: a second person with a different resume gets sensible results without editing JavaScript.
  5. Stage 5 — Make it learn (ongoing)
    Application analytics, source effectiveness, skill-gap rollup, learned sponsorship, embedding similarity, and interview prep generated from the gap analysis.
    Exit criterion: last month's outcomes measurably change this month's ranking.
Sequencing rationale

Stages 1 and 2 are prerequisites for trusting any measurement, and nothing after them can be evaluated without them. Stage 3 is placed before the intelligence work deliberately: better ranking on a funnel that terminates at zero produces better-ranked jobs nobody applies to. Prove one end-to-end submission before improving what feeds it.

Final verdict

JobAgent is a strong engineering project and an incomplete product, and the gap between those two things is unusually clean — which is good news, because it means the remedy is specific rather than architectural.

The engineering deserves real credit. The resume tailor is the best-designed component I examined: it refuses to write prose at all, and proves it with invariants that abort the save. The sponsorship handling is careful in exactly the places where carelessness would be harmful. The discovery layer reaches eleven ATS platforms without a single act of evasion, and documents its refusals. The comments explain why, with the measurement that forced the decision, more consistently than any codebase I have read recently. None of that is common.

The product is not finished, and two facts define the gap. First, the funnel terminates at zero: 101,857 jobs discovered, 4 packets prepared, 0 applications submitted in 54 days. The write half of the system has never completed a cycle, so its considerable safety machinery is untested by use. Second, the system is not yet safe for a second person: a fresh clone cannot run its own tests, and the configuration a new user is told to copy will type template text into an employer's work-authorization field while every guard reports success.

Those two facts are also why the scores land where they do. Nothing here needs rewriting. The four missing components in §16 are additions, not replacements, and the P0 list is short enough to finish in a week. The order matters more than the content: make it correct, make it honest, then close the funnel — and only then make it smart. Improving the ranking of jobs nobody applies to is the most expensive way to change nothing.

Get one application submitted end to end. Everything else in this report is easier to judge once that has happened.

Not validated — no live job-board request was issued during this audit, and no browser automation was run (Playwright Chromium is not installed on this machine). Two things this report got wrong

Both were found by measuring rather than re-reading, and both are recorded in the sections above rather than quietly amended.

1. The atsSearch detail budget was the wrong lever. §18 proposed raising maxDetailFetches for atsSearch “given 52% of rows arrive unreadable”. Per source, atsSearch has 0 of 331 rows under 200 characters — Workable returns the full JD inline. The unreadable rows are Workday (69%) and SmartRecruiters (70%), which together are essentially the entire gap. Those two budgets were raised; atsSearch was left alone with the measurement recorded next to it.
2. The duplicated study site was not merely drifted — one copy was broken. §19 noted that 5 of 12 interview-prep content files had diverged. The divergence was that four files under interview-prep/site/ contained literal newlines inside double-quoted JavaScript strings, which is a syntax error: npm run learn was serving a site where a third of the curriculum never loaded, while the dashboard's copy was fine and a CSS fix ahead. Deleting the broken copy fixed a live bug, not just duplication.

One finding also understated its own scope. §5 flagged the committed master resume; the same personal data was additionally hardcoded as DEFAULT_CANDIDATE_NAME in src/utils/outputPaths.js, so any caller that omitted candidateName named a second user's resume and cover letter after the author — in the documents sent to employers.
